## 一、项目定位与核心命题

### 1. 一句话定位

案隐盾面向律师使用外部大模型处理案件材料的场景，在特定法律任务下确定信息的最小披露范围，在外发前检验剩余再识别风险，并由律师对具体外发内容作出知情审批。

核心问题不是简单地“把案件材料脱敏后交给大模型”，而是：

> 为完成特定任务，哪些信息有必要离开本地环境？经过处理后，剩余信息是否仍可能识别当事人或暴露敏感事实？

### 2. 先期任务边界

- 目标用户：律师及律师团队。
- 首期场景：劳动争议案件材料的事实摘要辅助生成。
- 输入：案件文书、证据材料及必要的结构化信息。
- 输出：最小披露方案、风险检验报告、人工审批记录、具有原文依据的事实摘要与审计记录。
- 不定位为“全能法律助手”，不以胜诉预测、自动裁判或自动认定合法合规为功能目标。
- 评议书已完成，下一阶段重点是可运行系统、法律规则资产、验证证据与比赛交付。

### 3. 核心创新

以“任务驱动的最小披露”为主线，结合一致性假名化、再识别检验、知情人工审批、本地安全边界和原文回链。

“最小披露”是相对于已定义的任务、规则和候选方案作出的可解释判断，不应宣称已经证明数学意义上的全局最小值；再识别测试未成功，也不等于已经证明匿名化或绝对安全。

## 二、团队组织与并行分工

团队共6人：1名技术同学，5名法学同学。法学工作采用并行制，不采用逐人交接的顺序制。

| 角色 | 定位 | 核心职责 | 主要产出 |
| --- | --- | --- | --- |
| 技术负责人 | 战略负责人，类比董事长兼CTO | 战略方向、技术架构、技术取舍、全部技术实现与技术验证 | 系统、接口、部署包、技术测试结果 |
| 法学全局负责人 | 执行负责人，类比CEO | 日常推进、需求统筹、跨组协调、范围控制、验收和材料整合 | 统一需求、进度与风险台账、交付总包 |
| 法学同学1 | 法律规则与知识库 | 任务边界、字段必要性、依据整理、审批规则和责任边界 | 任务—字段—必要性矩阵、规则库、复核指引 |
| 法学同学2 | 数据与案例 | 样本构建、事实与证据标注、来源与授权整理 | 案例集、标注规范、标准答案、来源台账 |
| 法学同学3 | 评测与独立质检 | 红队协议、对照实验、盲测管理、失败案例和结果复核 | 测试协议、评分规则、实验报告、缺陷清单 |
| 法学同学4 | 产品表达与演示交付 | 用户操作流程、界面文案、演示案例、视频与操作说明 | 页面需求、演示脚本、视频、操作手册 |

运行原则：

- 技术负责人不承担所有日常催办；法学全局负责人不替代技术架构决策。
- 重大范围调整、对外效果主张和关键发布决定共同确认。
- 各工作流先约定共同的数据格式、版本与验收标准，再并行生产内容。
- 法学材料通过结构化规则、标注、测试和界面需求进入系统，而不是仅形成外围文字说明。
- 研发可以使用开发集；盲测答案和独立评分应保持适当隔离。

## 三、总体系统架构

### 1. 架构原则

采用“本地优先、任务驱动、规则约束的多智能体工作台”。

- 部署形态：以模块化单体为主，外发网关单独隔离；不在首期引入大量微服务。
- 编排方式：显式状态图控制主流程，局部任务可以并行，关键节点必须经规则校验和人工审批。
- 智能体负责需要语义理解的工作；权限、状态转换、审批有效性和外发控制由确定性代码执行。
- 多智能体是职责分工，不代表每个智能体都需要独立模型或独立服务。

### 2. 主流程与安全边界

```text
                    本地可信环境
┌─────────────────────────────────────────────┐
│ 案件建档与任务定义                            │
│          ↓                                  │
│ 文档解析 → 实体关系与事实证据结构化             │
│          ↓                                  │
│ 必要性判断 → 最小披露方案 → 候选外发载荷         │
│          ↓                                  │
│ 隔离红队测试 + 法律任务可用性检查               │
│          ↓                                  │
│ 硬性规则门禁 → 律师知情审批                    │
│          ↓                                  │
│ 外发网关：核验版本、审批、目标服务和发送状态      │
└──────────┬──────────────────────────────────┘
           │ 仅发送经批准的完整请求
═══════════╪══════════ 本地 / 外部边界 ═══════════
           ↓
       已登记的外部模型服务
           │ 返回结果
═══════════╪════════════════════════════════════
           ↓
    本地摘要校核 → 原文回链 → 人工确认与审计
```

材料被修改、风险未解决或测试无法完成时，应进入重处理、人工复核、转本地模型或停止流程，不能默认继续外发。

### 3. 必须区分的三组边界

1. 原始材料与外发载荷：原文、真实身份映射、内部理由和审批材料不随载荷自动外发。
2. 红队与评分真值：攻击智能体不能读取原文、身份映射或标准答案；独立评分模块才可读取真值。
3. 业务与实验：原文对照实验在隔离的本地评测环境运行，不进入真实外发通道。

## 四、多智能体职责与编排

| 逻辑模块 | 职责 | 主要约束 |
| --- | --- | --- |
| 任务理解智能体 | 将用户需求匹配到受支持的任务模板 | 不能自行扩张任务范围或修改已发布规则 |
| 案件结构化智能体 | 识别主体、关系、时间、金额、事实与证据归属 | 必须保留来源锚点，不得将推断冒充原文事实 |
| 披露方案智能体 | 根据任务与规则提出保留、替换、泛化或删除建议 | 输出逐项依据和不确定性，不能自行批准外发 |
| 红队智能体组 | 按冻结协议开展四类攻击 | 只可访问攻击者视图，受查询次数与工具权限限制 |
| 可用性与摘要校核智能体 | 检查主体关系、时间链、金额、证据和摘要事实 | 发现缺失、错配、虚构或无依据内容须显式报告 |
| 确定性控制模块 | 状态管理、规则门禁、审批校验、外发和审计 | 不以模型投票或自然语言承诺替代安全控制 |

建议以LangGraph一类支持持久化状态与人工中断的图编排框架实现，具体依赖版本在开发时锁定。人工审批与外部发送应拆为不同节点，防止恢复执行时重复产生外部副作用。

红队等局部任务可以并行，但需要设置并发上限、超时、重试预算与结束条件，避免无限反思或互相讨论。

## 五、核心数据结构与规则资产

### 1. 关键对象

| 对象 | 核心内容 |
| --- | --- |
| Case / TaskSpec | 案件标识、任务类型、目的、范围和输出要求 |
| DocumentIR | 文档版本、内容块、页码或段落/表格锚点、坐标、解析来源与不确定性 |
| EntityGraph / FactGraph | 主体及指代关系、事件、时间、金额、证据归属和原文引用 |
| DisclosureDecision | 字段必要性、变换方式、外发状态、规则依据与待复核事项 |
| PayloadVersion | 候选外发请求、版本、内容摘要值及依赖版本 |
| AttackRun | 攻击协议、攻击者输入、预算、过程、结果与独立评分 |
| Approval | 审批人、批准对象、时间、有效期、范围及审批决定 |
| SummaryClaim / AuditEvent | 摘要事实及来源、状态变更、异常和关键操作记录 |

完整回链应覆盖：

> 原文锚点 → 事实或字段 → 披露决策 → 外发内容 → 摘要陈述 → 校核结论。

### 2. 字段决策采用三个独立维度

- 必要性：必要 / 条件必要 / 不必要 / 不确定。
- 变换方式：保留原值 / 一致性假名化 / 泛化 / 删除。
- 外发状态：候选可外发 / 禁止外发 / 待人工复核。

例如，“保留劳动者与用人单位的关系”不意味着必须保留双方真实姓名或名称。是否保留精确日期、金额和地点，应结合具体任务判断，不作无条件的一刀切。

### 3. 知识资产分层

1. 法律与业务依据库：来源、适用范围、版本与复核记录。
2. 可执行规则库：任务—字段—必要性矩阵、禁止项、条件项、审批条件。
3. 任务知识库：劳动争议事实结构、证据归属规则和摘要模板。
4. 提示词与测试协议库：输入输出约束、攻击协议、评分规范。

规则发布需要人工审核和版本管理。上传文档中的指令属于待处理内容，不能成为系统指令。首期优先使用结构化规则与本地检索，不必为了形式完整立即引入向量数据库。

## 六、安全、人工审批与异常处理

### 1. 外发控制

- 仅外发网关具有调用外部模型所需的网络权限和密钥。
- 审批绑定完整请求，而不只是正文：包括消息、提示词模板、历史上下文、模型及服务商、相关参数和规则版本。
- 内容、目标服务或影响披露范围的参数变化后，旧审批失效。
- 普通审批不能绕过硬性禁止规则。
- 发送请求需要持久化状态和幂等控制；超时且发送结果不明时，不应盲目重发。
- 本地安全边界应由进程、网络和访问权限落实，不能只靠提示词约束。

### 2. 人工审批界面必须提供的信息

- 为什么保留该项信息，以及对应任务需要。
- 删除或泛化会损害哪一类事实关系。
- 当前残余风险和攻击检验发现。
- 具体准备发送的完整内容与目标服务。
- 可选操作：删除、修改、重新测试、转本地处理、批准外发或停止。

### 3. 关键异常策略

- 解析失败、低质量OCR或来源不完整：提示修正或人工复核。
- 红队超时、工具异常或结果不确定：标记为未完成/不确定，不能记为通过。
- 规则冲突或必要性不明确：进入复核，不由模型自行补造规则。
- 外部模型无响应：保留执行状态并提示，不默默变更服务商。
- 返回摘要包含无来源事实：标记问题并阻止其被直接作为已核实结果交付。
- 重启恢复：不能重复外发、跨案件串用身份映射或丢失审批关联。

日志尽量使用标识与引用，不记录无必要的原文和密钥。哈希链可以帮助发现篡改，但不能单独宣称日志不可篡改。

## 七、前端、后端与部署建议

### 1. 前端

建议使用npm管理依赖与构建命令，采用React + TypeScript + Vite。npm是包管理与脚本工具，不是完整前端架构本身。

产品形态为法律工作台，而不是只有聊天框的通用助手。建议划分五个工作区：

1. 案件与材料管理。
2. 任务定义与披露方案。
3. 风险测试与律师审批。
4. 事实摘要与原文校核。
5. 实验结果与审计展示。

核心页面采用“原始材料—当前结果—依据与操作”三栏结构，加流程阶段条；始终明确标识本地内容、待外发内容与已外发内容。实时运行、历史回放与模拟数据必须显式区分。

### 2. 后端与存储

- Python + FastAPI提供业务接口。
- 状态图编排任务，后台工作进程执行耗时任务。
- 本地模型服务可以被多个逻辑智能体复用。
- 初期可采用SQLite及本地文件存储，但必须处理写入并发、任务归属、重启恢复与备份。
- 流程检查点保存执行进度；业务数据库保存材料版本、审批和审计，两者职责不同。
- 前后端可通过SSE推送进度，服务端状态为准，并支持断线恢复。
- 一个代码仓库，按API、工作进程、外发网关与模型服务分离运行职责。

### 3. 文件处理边界

首期优先打通DOCX和文本型PDF；扫描材料根据硬件与工期分阶段支持。

文档解析必须保留段落、表格、页码及证据锚点，混合型PDF按页判断处理方式。首期外发内容采用重新序列化的结构化文本，不直接发送原始附件。若支持脱敏文件导出，需另外验证隐藏文本、元数据等是否残留；视觉遮盖不等于底层内容删除。

## 九、验证设计与比赛演示

### 1. 数据与对照

- 计划构建100份半合成劳动争议案例：参考真实案件结构，重新组合人物与具体事实。
- 有意识加入岗位、地点、日期和少见事件组合等可链接线索，并配套冻结的辅助信息集。
- 标注采用双人独立标注、分歧复核；建议按70/30划分开发集与盲测集，并防止模板及关联身份泄漏。
- 保留四组对照：原文、查找替换、一致性假名化、任务驱动最小披露。
- 原文组只在本地隔离环境评测。实验应说明该设计对外部模型场景结论的适用限制。

这些属于待实施的验证设计，不是已经完成的数据或实验结果。

### 2. 冻结红队协议

四类攻击：身份恢复、候选集合缩小、敏感事实推断、跨轮关联。

每类预先规定攻击者可见资料、可用工具、查询轮数、时间预算、成功标准和猜测的判定方式。攻击者获得实际拟外发请求及协议允许的历史披露，不得获得内部真值。一般运行不直接使用真实案件线索做互联网搜索，避免搜索请求本身造成额外披露。

结果区分：攻击成功、未成功、不确定、执行错误；不把后两者计为安全通过。

### 3. 三维评价

| 维度 | 关注内容 |
| --- | --- |
| 隐私风险 | 四类攻击结果、候选集合变化及风险残留 |
| 法律任务可用性 | 主体关系、时间链、金额、证据归属、摘要准确性与完整性 |
| 流程成本 | 处理时间、人工复核时间、修改轮次、调用成本和阻断率 |

报告必须包含失败、阻断和无法完成的样本，不能只报告获准外发案例。记录数据、模型、提示词、规则和攻击协议版本，所有效果数字均来自实际运行与复核。

### 4. 三个核心演示案例

1. 普通成功案例：完整展示输入、处理、审批、摘要与原文回链。
2. 表面脱敏仍可识别案例：显示仅替换姓名的不足，以及组合线索风险。
3. 主动停止案例：风险无法充分降低时，拒绝外发或转本地处理。

## 十一、下一步应优先冻结的事项

### 1. 四份共同接口规范

1. 文档与来源规范：DocumentIR如何表达段落、表格、页面与原文锚点。
2. 字段决策规范：必要性、变换方式、外发状态及法律/业务依据如何表达。
3. 外发审批规范：审批绑定哪些内容，何时失效，如何阻断未经批准的发送。
4. 攻击者视图规范：红队可以看到什么，评分模块持有什么，如何防止真值泄漏。

### 2. 尚待确认的落地条件

- 比赛截止日期与开发周期。
- 部署操作系统、可用显存/内存和演示设备。
- 本地模型、外部模型服务及可接受的调用成本。
- 首期文件类型、材料规模与并发要求。
- DataInfra实际复用范围及相应授权。
- 具体劳动争议任务模板、字段矩阵与风险阻断规则。

### 3. 首期验收底线

先用三个代表案例跑通完整链路，证明：任务范围明确、字段决策有依据、攻击者与真值隔离、未经批准不能外发、内容修改使旧审批失效、摘要可回到原文、系统能够真实停止、运行证据可复核。

系统的完成度不以智能体数量衡量，而以法律任务、安全边界和验证闭环是否真实运行衡量。
