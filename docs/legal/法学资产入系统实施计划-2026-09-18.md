### 2.2 `manual_review_conditions` 升级为结构化

现在是 `list[str]`，五条自由文本（`法源未冻结`、`规则必要性不确定`、`攻击协议未完成`、`解释（二）适用时间不明`、`条件未知已限制输出而非默许外发`），且**全仓库只有 `contracts.py:175` 定义它，没有任何代码读取**——是死槽位。

新增 contract：

```python
class ManualReviewCondition(Contract):
    id: str = Field(pattern=r"^[a-z][a-z0-9_]{1,80}$")
    trigger: str                      # 复核触发情形
    why_machine_cannot: str           # 为什么机器不能直接下结论
    what_to_verify: list[str]         # 律师要核什么（逐项，不得只写"风险较高"）

    gate_id: Literal["G0", "G2", "G3", "G5", "G7", "G8", "G9"]  # 只能落在既有 G 表

```

字段改为 `manual_review_conditions: list[ManualReviewCondition]`。修订版给的 11 类逐条导入：特别法适用无法确认、处分权限不明确、保密义务范围不明确、司法/仲裁保密措施不明确、AI 服务商处理关系不明确、是否跨境无法确认、规则真实冲突、重识别风险无法确认、决定性事实缺失、涉密属性不明确、去标识化是否达匿名化无法确认。

### 2.3 两张映射表的落点与真实覆盖率

25 类个人信息 + 15 类其他敏感客体**不能**直接变成 `disclosure_rules`：现有 36 条规则的键是（任务 × 子目的 × `fact_field`），而 `fact_fields` 只有 11 个（`entity`/`relation`/`event`/`date`/`amount`/`evidence`/`claim_stance`/`day_nature`/`overtime_hours`/`wage_base`/`evidence_holder`），粒度比 25 类粗得多。

建议新增一层 `sensitive_object_rules`（新 contract），按"信息类型/客体"索引，不动 `disclosure_rules`：

```python
class SensitiveObjectRule(Contract):
    id: str
    object_type: str                  # 如"身份证件号码"、"企业商业秘密-技术信息"
    object_group: Literal["personal_information", "other_sensitive_object"]
    carriers: list[str]               # 常见载体/出现位置
    is_sensitive_pi: bool = False
    default_handling: str             # 默认处置口径
    detector_categories: list[str]    # 可自动命中的 detection category，可为空
    review_condition_ids: list[str]   # 指向 manual_review_conditions
    legal_source_ids: list[str]
    rule_nature: Literal["statutory", "standard_reference", "project_control"]
```

**必须在计划里讲明的覆盖率事实**：`detection.DEFAULT_PATTERNS` 只有 5 个类别（身份证号、手机号、电子邮箱、银行卡或长编号、姓名），且 pack 的 `direct_identifier_patterns` 当前为空数组。也就是说 25 类个人信息里**只有 5 类**有冻结的确定性模式可自动命中；其余 20 类（医疗健康、行踪轨迹、生物识别、未成年人、绩效奖惩等）属语义判断，导入后只能作为复核清单和默认处置口径存在，**不会自动检测、不会自动阻断**。15 类其他敏感客体同理，全部依赖律师在字段上声明。导入这两张表不等于获得自动覆盖，文档与界面都不得这样表述。

## 3 第三步：四态派生（不改判定，只改结论表达）

### 3.1 问题

`policy.assess` 返回 `blockers: list[str]` 加 `approval_allowed = not blockers`，二态。文档要求四态：允许处理 / 补充脱敏后允许 / 补充核实 / 禁止外部处理。现在这四种情况全挤在同一个 `blockers` 列表里，看结果说不出下一步该找律师、该改脱敏，还是该等工程就绪。

一个具体例子：字段标了 `confidentiality_category="state_secret"` 时，`disclosure.apply_material_restrictions`（`disclosure.py:736`）会把它删空并置 `status="restricted"`，于是产出 G0 消息「存在尚未解决的字段复核事项或已被规则限制的字段」——把**已确认的国家秘密禁止**和**普通待复核字段**说成了同一句话。

### 3.2 做法

给每条 gate hit 增加 `kind` 字段（`_hit()` 加一个参数），**不改任何 hit 的产生条件**：

| kind | 含义 | 下一步 |
| --- | --- | --- |
| `prohibition` | 四要件完整成立，法律直接禁止当前行为 | 不得外发；换合规环境或先取得授权 |
| `verification` | 决定性事实或依据未查清 | 暂停并交人工核实具体问题 |
| `minimization` | 可通过删除/泛化/裁剪消除 | 改脱敏方案后重新校验 |
| `engineering` | 工程或治理未就绪，**不是**对材料的法律判断 | 工程侧补齐；不得表述为法律禁止 |

派生两个正交字段：

- `disposition: Literal["allowed","needs_minimization","needs_verification","prohibited"]`，只由 `prohibition`/`verification`/`minimization` 三类派生，从严取最高：prohibition > verification > minimization > 无。
- `system_readiness: Literal["ready","not_ready"]`，由 `engineering` 类派生，**不占 disposition**。

这样设计的原因：当前仓库状态下 G5 权重未冻结、G8 攻击未跑、G9 隔离未验恒定存在，若让 engineering 参与 disposition 排序，所有正式案件永远显示"系统未就绪"，法律层面的结论会被永久掩盖。拆成正交两维后，四态保持四态，工程就绪度单独表达。这也正好对应说明书第九章「仅有合同/服务商规则禁止 → 性质不必然是法律禁止，应单独记录」。

`approval_allowed` 仍然是 `not blockers`，等价于 `disposition == "allowed" and system_readiness == "ready"`。**放行条件一个字不改。**

### 3.4 `prohibition` 的唯一合法来源：四要件结构化

现状核实：pack 的 11 条 `rules` 中 `forbidden` **全为 `False`**，`RESTRICTED_CONFIDENTIALITY` 只含 `state_secret`。也就是说运行时目前**不存在任何 `prohibition` 类 hit**，四要件硬性禁止在代码里还没有表达形式。

修订版的 5 类硬性禁止（国家秘密、法院/仲裁具体保密措施、商业秘密＋明确第三方限制、传染病特别规则、其他特别法）全部要求四要件确认，机器判不了。因此 `prohibition` 只能由律师声明产生，绝不能由关键词或类别标签产生。新增 contract：

```python
class ProhibitionFinding(Contract):
    category: Literal["state_secret", "court_confidentiality_order",
                      "trade_secret_restriction", "communicable_disease", "other_special_law"]
    protected_object_confirmed: bool = False       # 要件1 明确受保护对象
    rule_prohibits_current_act: bool = False       # 要件2 规范直接禁止当前行为
    applies_to_current_context: bool = False       # 要件3 适用当前主体/材料/方式
    minimization_insufficient: bool = False        # 要件4 最小化不能脱离禁止范围
    legal_source_ids: list[str] = Field(default_factory=list)
    basis_note: str = ""
    confirmed_by: str | None = None
    confirmed_at: str | None = None
```

判定：四个布尔全 `True` **且** `legal_source_ids` 含至少一条 `rule_nature="statutory"` 时，出 `kind="prohibition"`；任一不成立则出 `kind="verification"`，消息写明缺哪个要件。

对既有行为的影响需要明确：`state_secret` 字段今天是标了就阻断。改造后，若四要件没填满，它从 `prohibition` 变成 `verification`——**但两者都进 `blockers`，`approval_allowed` 都是 `False`**。`apply_material_restrictions` 的删空和 `status="restricted"` 行为完全不动。fail-close 不变，变的只是结论文案与下一步动作。
