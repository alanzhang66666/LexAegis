# LexAegis · 案隐盾

## 理想运行状态提案

版本 V1.0（`1.0.0`）。非正式发行说明。执法只走 `outbound_gate` 的 G 表。不新增第二套门禁编号，不削弱 `validate_formal_gate` 与 `authorize_dispatch`。

这份文件描述系统应当长成的样子。它不是当前验收结论，也不是发送授权。今天 `formal_dispatch` 仍是 `blocked`，既有十案仍是层 A、0 案真实正式发送。

### 1. 这套系统要成为什么

案隐盾是本地优先的法律披露工作台。原文、身份映射和内部理由留在边侧。云端只收到已经最小化、已经冻结、并且这一次请求被批准的事实。云端的活是按这些事实生成摘要。摘要回到边侧之后，再用本地映射把 token 对回身份，并逐条核对外发事实。

理想状态下，律师能完成一次完整案件：整理材料、确认事实、生成披露方案、过边侧审核、做人工复核、在条件齐备时批准并发送一次、取回结果并回链原文。发送失败、材料变化、复核否决，都停在当次请求上，并留下可核对的记录。

### 2. 谁做什么

| 角色 | 理想职责 |
| --- | --- |
| `case_operator` | 建案、确认事实、生成披露方案、在已批准后执行发送 |
| `technical_reviewer` | 指出组合线索或材料问题，提交后当次请求暂停 |
| `legal_reviewer` | 阅读边侧底稿，修改后具名提交复核结论。允许处理不授予发送权 |
| `approver` | 对同一 `request_hash`、同一门禁快照作一次 G10 批准 |
| `admin` | 安装停在 `blocked` 的单次策略，管理本地账户。不能代替法学复核人或审批人 |

边侧模型不是这些角色里的任何一个。它只做三件本地的事：从材料抽出可回链的事实候选；判断候选能否进入人工复核；按冻结事实和规则包起草复核底稿。`allow_human_review` 只表示可以给人看。底稿的 `recorded` 恒为假，`grants_dispatch` 恒为假。

### 3. 一条请求的理想路径

材料进入边侧，解析成带锚点的原文块。低质量 OCR 或转写未复核时，不能抽取，也不能批准。事实经人确认后，按案由包逐项决定保留、泛化或删除。外发文本使用 `[[LEX:P0001]]` 这类 token。mapping、原文、anchors、`local_text` 不进入发给云端的报文。

然后固定走三条链路，三条都先创建为可云端的请求，但前两条不得离开本地：

1. **边侧不能发。** 模型或安全基线给出 `block_external`。人工复核不到达。终态 `blocked`。不调用云端。身份证号、手机号加可重识别线索、字符序列「唯一」「公开获奖」「公开表彰」，都停在这里。「技术表彰」不算「公开表彰」。普通工资争议（用人单位、劳动关系、合同日期、工资月份、金额）应到达人工复核。
2. **边侧能发，人不能发。** 边侧为 `allow_human_review`。`legal_reviewer` 否决当次请求。终态 `rejected`。不调用云端。否决只针对这一次请求，可另建后继任务。
3. **边侧和人都认为能发。** 边侧为 `allow_human_review`，法学结论为允许处理，具名审批人批准这一次完整请求。成功标准是任务 `complete`，`transport=cloud`，结果 `provenance=cloud`。云端摘要的顶层字段是 `claims`，每条有 `text` 和 `source_ids`，并带回 `unused_fact_ids` 与 `gaps`。边侧本地计算未使用事实，核验缺口，不把模型输出自动再发一次。

`demo` 档案禁止 cloud，只能做离线演示。第三条的真实发送发生在 `integration` 或已武装的 `production` 上。缺云端槽位时失败关闭，不退回本地模拟。

### 4. 人工复核在理想状态下怎么省力

边侧第二次推理只读已冻结事实和当前规则包，按现有栏位写底稿：理由、事实前提、权限判断、外部处理条件、最小化措施、最终依据、适用边界。证据 id 必须来自输入。法源和复核事项只能选自规则包，选不中就留空。

页面把底稿填进现有输入框，并标明这是草稿。结论单选框不自动勾上。复核人改错处后，以 `legal_reviewer` 身份提交。缺字段、错法源、错证据照旧拒绝。`block_external` 或安全基线改判时，不展开这张长表，也不生成底稿。

底稿变化不调用 `authorize_dispatch`，也不改 `formal_dispatch`。

### 5. 正式外发在理想状态下如何打开

没有全局开关。无参数的 `product_dispatch_state()` 始终返回 `blocked`。能力面板上的 `formal_dispatch` 因此也始终是 `blocked`。

能变成 `armed_once` 的只有这一次请求，范围只有：

`LA-001 × R_fact_summary × D_DeepSeek_official_API`

顺序是：

1. 在 `production` 上冻结这一次真实请求。目标是精确 HTTPS 地址和模型，主槽是 DeepSeek 官方 API。`demo` 合成案不进入这条放行。
2. 构建清单 `status=verified`。工作树干净，源码、文档、前端、wheel、锁文件、运行包哈希一致。`pending` 清单不能武装。
3. 具名 `admin` 安装一条策略。`maximum_dispatches=1`，安装时状态必须是 `blocked`，并绑定构建哈希、服务商档案哈希、目标和模型。
4. 同一 `request_hash` 上具备有效签署件：`G1`、`G2`、`G3`（法03 与法04）、`G5`、`G6`、`G7`、`G8`、`G9`、`G10`，外加一份隔离部署收据。`G2` 含 LA-001「本次可用」整句和组织的真实材料授权。`G8` 是法学对四类冻结攻击的具名 `resisted`。隔离收据绑定当次请求、五项探测、宿主机防火墙和镜像供应链，并由法学确认。native 不能自证隔离。历史 Compose 探测不能代替当次收据。
5. `evaluate_release` 达到 `approval_eligible` 后，具名 `approver` 签发一次性许可。策略此时才变为 `armed_once`，有效 30 分钟。入队和 worker 发送都重验 `authorize_dispatch`。网关先验签、先占用许可，再调用云端。用完变为 `consumed`，自动回到关闭。异常若不能证明请求未离开本地，记为 `unknown`，不盲重发。

其余九案继续由 G2 层 B 关闭。一次 LA-001 成功不扩成十案。备用槽不因这一次成功而打开。每一案、每一次后续请求都要重新冻结、重新过门、重新批准、重新消费许可。

系统不代填合同、服务商 `reviewed`、PIPIA、攻击 `resisted`、隔离结论或法学签署。缺证据保持 `unknown` 或 `pending`，并继续阻断。409 表示门禁在工作。

### 6. 理想状态下仍唯一的门

| id | 理想状态下要证明的事 |
| --- | --- |
| G0 | 请求卫生：直接标识、未确认事实、OCR、预算、边侧阻断 |
| G1 | 法源采用经过具名来源人审，并绑定证据哈希 |
| G2 | 仅 LA-001 本次可用且有组织真实材料授权；其余九案关闭 |
| G3 | 本账号服务商事实、处理条件、PIPIA、D 主槽精确绑定 |
| G5 | 运行库规则已发布，范围、法源、五类权重和内容哈希冻结 |
| G6 | 完整请求、依赖、材料、累计披露和构建清单冻成一个 `request_hash` |
| G7 | 同哈希组合检测，加上法 08 的具名结论。工程未命中不等于法学通过 |
| G8 | 同哈希四类攻击运行，且法学逐项 `resisted` |
| G9 | 同哈希的请求级隔离收据。全局 `isolation_verified` 不能单独放行 |
| G10 | 具名审批人对同一哈希、同一快照批准一次 |
| G-product | 已安装、未撤销、未消费的单三元组策略，剩余次数为 1。发送后回闭 |

批准前用 G0 至 G9 加 G-product 计算能否进入批准。批准后同一张表加上 G10，才计算能否发送。法学复核页的「允许处理」不是 G10。

### 7. 云端与回边在理想状态下的契约

主槽是 `api.deepseek.com` 上的 `deepseek-v4-flash`，地址 `https://api.deepseek.com/v1/chat/completions`。密钥只在网关。边侧进程看不到云端密钥。

事实摘要提示要求顶层 `claims`，禁止 `statements`。本地校验失败则任务 `failed`，即使 HTTP 已返回。未使用事实和缺口进入案件待办，由人忽略或另开后续披露。

默认导出不含身份的 `cloud_view`。含身份的 `local_review_bundle` 需要逐项确认，再加一次绑定任务版本和产物哈希的短时具名确认。

### 8. 理想状态明确不做的事

- 不把产品闩改成全局 enabled。
- 不把仓库草稿包直接改成 `published`。
- 不把口述、空表或模型底稿写成服务商 `reviewed` 或法学 `resisted`。
- 不把工程攻击运行写成法学 `resisted`。
- 不把「10 案已通过」或「外发已开通」写进状态。
- 不把审批页接到第二条发送路径。
- 不因一条合成 `integration` 请求的 `provenance=cloud` 视为正式放行。那次请求的 `product_release` 是 `not_applicable`。

### 9. 怎样算达到这份提案

同时满足下面五条，才算理想运行状态达到，而不是只算代码里有这些函数：

1. 三条链路在 `integration` 上可重复：前两条不发送；第三条 `complete` 且 `provenance=cloud`。
2. 法学复核人在页面上能用边侧底稿完成核对并具名提交；底稿本身不出现在复核记录里。
3. `LA-001 × R_fact_summary × D_DeepSeek_official_API` 能在证据齐备后武装一次、消费一次、自动回闭。无参数 `product_dispatch_state()` 仍是 `blocked`。
4. 十案里只有取得「本次可用」和全部门禁的那一案可以讨论这一次发送。其余九案保持关闭。
5. 任何缺失签署、脏工作树、过期许可、哈希变化，都返回阻断，并且不退回 mock。

当前还停在第 1 条的一次合成实测，以及底稿功能已接入页面。第 3 条到第 5 条依赖真实签署件和干净构建，系统不能代填。
