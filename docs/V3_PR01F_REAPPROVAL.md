# V3 正式许可重新审批准备

对于仍处于 `approved`、尚未排队的正式云端任务，具名审批人可在风险工作台填写原因，调用 `POST /api/v1/tasks/{task_id}/formal-release/reapproval`，提交当前 `request_hash` 和原因。接口使用现有登录会话和严格 `approver` 角色；管理员、技术或法学角色不能代行。原因记入审计，不应包含案情原文。

服务端在单个 SQLite 写事务内校验任务和案件版本、当前冻结请求、风险及人工复核约束、许可和策略关联；任何已领取记录、同策略其他未结束许可、发送作业或披露记录都会阻断。合格时只撤销或保留已撤销/过期的旧许可，将未消费策略恢复为阻断，清空当前批准并回到 `review`，记录具名操作；此动作不签发新许可、不批准、不发送。已有的有效门禁、同请求 G10 收据和具名审批流程仍然全部适用。旧许可及审计历史保留。

若任务已排队、发送或出现不确定状态，本接口不会重开策略或重发；需按现行网关核对和任务处理流程处理。撤销旧收据后若证据仍不足，重新审批依然会被门禁拒绝。实际目标环境的密钥、人员授权和真实案件验收不由合成测试代替。
